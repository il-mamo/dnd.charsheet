# DnD.CharSheet — technical specification

Status: BASELINE v1 — owner scope decisions confirmed 2026-10-20. Task 1.1 implementation status is recorded in section 7 and docs/tasks/1.1.md.

## 1. Purpose and boundaries
Windows desktop application for a single player's multiple D&D characters, following PHB 2024. Always used from the player perspective; there is no DM mode or role selector. The player records outcomes adjudicated by the DM. Local SQLite database. C#/.NET with WPF/MVVM; offline, single-user operation. Intended for private use only. Fast identity-safe switching during play. No Jira integration. DM adjudicates target AC, success/hit and world effects; application explains the character's rolls/effects and tracks confirmed character state.

Confirmed original requirements use R IDs; accepted additional requirements retain P IDs for stable traceability. All R and P requirements are in v1 scope. Source verification must precede encoding handbook mechanics.

## 2. Confirmed decisions and implementation defaults
- D1 CONFIRMED: Full PHB 2024 classes, subclasses, species, backgrounds, feats, spells and equipment through levels 1–20, including multiclassing. Incremental delivery is permitted; reduced final coverage is not. PHB features requiring companion/summoned/transformed creature information must include the relevant PHB stat blocks and character-state effects. This is not an encounter manager.
- D2 CONFIRMED: C#/.NET, WPF/MVVM and SQLite; offline, single-user operation. Select and pin a supported SDK/package baseline during architecture task after checking installed tooling and official support information.
- D3 CONFIRMED: Private use only. Supplied PHB PDF is accessible; see section 6. Keep PDF, page renders and extracted private catalog out of GitHub. Public repository code must support loading the local private catalog without bundling book content.
- D4 CONFIRMED: P01–P07 are included in v1, including backup/restore, leveling, rests, conditions, spell resources, accessibility and session history.
- Defaults: external physical dice with manual input; no built-in dice roller required. Enter the final roll total in a clearly labelled field; optionally record natural die values when a rule depends on them, without inferring them from totals. DM success/hit remains explicit. Users confirm critical status when relevant.
- Defaults: level 1 guided creation plus existing-character entry at levels 1–20; XP tracking and DM-directed level advancement; HP advancement supports entered rolls or verified fixed values. Do not force XP thresholds when the DM awards a level.
- Defaults: Windows 11 x64, 1920x1080 display at 100% Windows scaling only (owner decision 2026-10-20; no smaller-resolution or scaling variants required), per-user data under LocalApplicationData/DnD.CharSheet. Package and update strategy must be documented in task 0.3; no auto-update service required. Other architectures/Windows versions are not acceptance targets without a scope change.
- Defaults: backup is a versioned ZIP containing a manifest, consistent database snapshot and managed portraits; character export is a versioned JSON document plus assets in a ZIP. Restore previews and validates before replacement; character import creates new IDs by default. No arbitrary code or absolute/path-traversal entries may be imported.
- Optional-rule boundary: support PHB choices needed for the agreed character flows, including multiclassing and all three ability-generation methods. DM-discretionary outcomes are recorded explicitly. Older-book compatibility remains excluded; a reference to it in the PHB does not expand the catalog. Any unresolved discretionary variant is clarified at its bounded task, not silently enabled.

## 3. Confirmed functional requirements
- R01 Character library: create/manage multiple characters within the selected Adventure; recognizable portrait/name; switch quickly without state leaking between characters. Keep unsaved input safe and bind mutations to character ID even if selection changes.
- R02 Portraits: import/update local image; managed copy, preview, fallback, supported-format validation and reasonable size limits. Missing original file must not break saved portrait.
- R03 Guided creation: ordered screens matching the verified PHB Creating a Character process (section 9); progress, back navigation, prerequisite validation and resumable draft. Distinguish incomplete drafts from playable characters.
- R04 Existing character entry: enter existing level and all relevant choices/stats/resources; verify consistency and flag incomplete information. Never silently reroll, reset or overwrite supplied values.
- R05 Character sheet: neatly section identity, ability scores/modifiers, saves/skills, class features, feats, species traits, inventory, equipment, weapons, spells and other applicable character details. Explain calculated modifiers and their sources. Weapons show their properties, permitted wielding modes with corresponding damage, and mastery effect with character-specific availability (section 13).
- R06 Battle mode: prominent HP/status/resources and categorized actions, bonus actions, reactions plus relevant contextual options. Derive options from character choices, equipment, resources and verified rules. Do not imply all features share identical action costs.
- R07 Dice workflow: select action and weapon/spell/feature as needed; show roll expression, accept reported roll and DM success/hit outcome, then show applicable effects/damage expression. Example dice expressions in the brief are illustrative, not weapon rules. Use the roll-entry contract in section 2; label totals and natural dice distinctly. Cancellation or duplicate confirmation must not accidentally spend resources. Do not determine enemy AC or automatically apply enemy damage.
- R08 Finder: readily accessible search across ability scores, skills, saves and applicable checks; partial case-insensitive names such as Perf find Performance and its signed modifier. Show score plus modifier for six abilities; modifier-only entries remain clearly distinct. Reuse central calculations.
- R09 Status: current/max HP, relevant temporary HP, death save successes/failures and limited-use resources; show used/remaining/max and recharge trigger. Persist resources independently for each character. Verify actual resource maxima/recharge rules; brief examples do not establish handbook values.
- R10 Inventory: search verified catalog; add/remove quantities; inspect item details; equip/use applicable items; create DM custom items with descriptive and structured mechanical fields. Label provenance. Deleting catalog references must not corrupt existing character items.

- R11 Adventures (owner amendment 2026-10-20): an Adventure groups one or more characters. Each character belongs to at most one Adventure. Characters retained after Adventure deletion can be unassigned and remain stored, but cannot be used until assigned. At the beginning of every application session the player explicitly selects an Adventure before opening any character or gameplay screen. Adventure management provides creation with its first character, listing, renaming, deletion and character membership management. Deleting an Adventure unassigns all its characters without deleting their data. A character can be transferred to another Adventure, preserving its identity, portrait, progression, inventory, resources and history; transfer moves membership rather than copying the character. Adventure selection is session context, not a reset/rest or rules modifier. No multiplayer, DM account or encounter-management scope is added. See section 12 for integrity, implementation slices and confirmed lifecycle policy.

## 4. Accepted additional v1 requirements
- P01 Autosave validated changes transactionally; recover drafts after restart; visible save failure and retry; never silently lose data.
- P02 Explicit short/long rest workflow with preview of affected resources and confirmation; apply each resource's verified recharge rules. Track conditions, exhaustion, concentration and death-state transitions where applicable.
- P03 Level advancement with choice/prerequisite checks and explicit handling of prior-level mistakes. Include multiclassing with prerequisites, distinct class/total levels, correct feature interactions, mixed Hit Dice and spell resource rules.
- P04 Spell preparation/known spell bookkeeping, slots and other casting resources, concentration and resource expenditure where applicable to supported classes. Casting includes explicit resource/slot-level selection and a spell-specific list of higher-level effects and costs before confirmation (section 13).
- P05 Versioned backup/export and restore/import covering characters, portraits and custom items; validate before mutation, back up before migration/restore, preserve existing data on failure. Portable character export for transfer.
- P06 Keyboard navigation, labelled inputs, readable UI at the supported 1920x1080 / 100% display target, clear signed modifiers, non-color status cues and offline operation with no required account/network.
- P07 Basic currency, ammunition and consumable tracking; spending/use only on explicit confirmation. Session history for recent character mutations to explain changes; History is an audit aid; unrestricted undo is not required. Provide explicit correction controls for current HP/resources and preserve the correction in history.

## 5. Architecture and data contracts
Confirmed stack; architectural boundaries: desktop presentation → application use cases → pure domain/rules → SQLite/files infrastructure. UI must not duplicate rule calculations or issue SQL directly. Use stable IDs, foreign keys, schema migrations, transactions and explicit units. Store mutable character state separately from versioned verified catalog content. Preserve rule-source references and overrides with reasons. No runtime LLM dependency.

Model Adventures with stable identities and names, zero-or-one Adventure membership for each character, with unassigned characters unavailable for play, characters, progression/choices, ability values/proficiencies, features/resources/recharge policies, items/equipment, spellcasting, conditions, portraits and source citations. Schema details belong to bounded design tasks. Calculated values derive from a shared service; represent proficiency/expertise/overrides explicitly. Store portrait assets in managed local application data, not arbitrary source-file references. Installation data location: user-local application data (section 2); keep live databases and private source content out of source control. Backups must include Adventures, memberships and referenced assets. Character import requires an explicit destination Adventure; never match or create membership by display name. Full restore preserves the Adventure/character graph and validates assigned membership references and preserves legitimate unassigned characters before replacement. No cloud sync, telemetry, multiplayer, DM encounter manager, virtual tabletop, automated enemy resolution, homebrew class builder or 2014 compatibility in baseline v1.

## 12. Adventures and player perspective - amendment 2026-10-20
Status: R11 and player-only perspective confirmed by owner; not implemented. Existing library/switching acceptance predates Adventures and is not proof of R11 compliance.

### 12.1 Integrity and session behavior
- Adventure is a first-class local entity with stable identity and editable display name. Assigned membership is single-valued; unassigned characters are retained but cannot be used. Adventure contains at least one character, counting drafts. Adventure creation includes its first character: atomically create a new character/draft or assign an existing unassigned character. Display names are not identity keys.
- Launch opens Adventure selection. Last-used Adventure may be highlighted but must not be silently selected, including when only one exists. Character continuation, draft recovery, creation and import occur after Adventure selection. Settings, backups and Adventure management are accessible before selection.
- Character library, recent characters and character switcher are scoped to the selected Adventure. Shell displays both Adventure name and active character identity. Switching Adventures clears the active character before exposing the new roster. Pending edits stay bound to their original character and Adventure; selection never redirects writes.
- Transfer requires source character, source Adventure, destination Adventure and explicit confirmation. Validate current membership and destination at confirmation; apply the move atomically, once. Failure/cancel preserves membership and all character state. Source/destination rosters refresh only after success; an active transferred character is deactivated in the source session. Destination Adventure is not automatically selected. Record the move in character history when that facility is implemented.
- Backup/restore covers Adventures and memberships. Import creates a new character identity by default in the explicitly chosen destination; export remains portable and must not auto-create an Adventure based on a name. Restoring must reject invalid references to nonexistent Adventures (legitimate unassigned characters are permitted) without replacing existing data. Older archive compatibility and existing-data migration must be designed explicitly before implementation.
- Adventure deletion explicitly previews that all members will be retained as unassigned and unavailable for play until reassigned. Confirm atomically unassigns members and removes only the Adventure; cancel/failure preserves both. Clear the active Adventure/character if affected. Never cascade-delete character data.
- Assigning an unassigned character requires an existing destination Adventure and explicit confirmation; validate destination and unassigned status at commit. Assignment changes membership only. No battle, sheet use, resource changes or draft continuation before assignment; management preview, export, and assignment remain accessible.
- A transfer or individual character deletion that would leave an existing Adventure empty is blocked; offer explicit Adventure deletion, which retains its members, before reassignment. Do not silently remove the Adventure or violate its nonempty invariant.

### 12.2 Confirmed lifecycle policy
Owner confirmation (2026-10-20): create Adventure together with its first character. The first member may be a newly created character/draft or an existing unassigned character. Deleting an Adventure retains all characters with no Adventure assigned; they cannot be used until assignment. No cascade deletion. Existing pre-Adventure characters migrate without data loss into this unassigned management state and must be assigned before use; do not invent membership or silently create an Adventure. Migration uses a safety snapshot. Unassigned state is deliberate and distinct from a broken reference. Creation, deletion, assignment, transfer and restore must preserve these invariants transactionally.

### 13.2 Casting requirements
- Show spell base level separately from selected casting level and resource source. Select a legal available slot at or above base level. No universal increase-damage formula. Preview named effect changes from the selected spell's verified higher-slot clause: damage/healing, projectiles, targets, duration, concentration, bonuses or other changes as applicable. Include resulting values and relevant target/choice controls. If no enhanced effect is specified, say No additional higher-slot effect; selected casting level still applies.
- Keep normal Spellcasting and Pact Magic resources distinct; validate availability and feature-specific permitted source. Do not conflate cantrip character-level scaling with upcasting. Ritual, item and limited-use casting follow their own verified method/level rules; do not expose an arbitrary slot selector for them.
- Display one selected resource expenditure before confirm; preview/level changes do not spend. Exhausted/too-low/unsupported options show concise reasons. Revalidate resource and captured character/Adventure at confirmation; cancel, failure and duplicate confirmation must not accidentally spend. History records spell, casting level and resource source.
- Rules for every spell/feature must be verified in its content task. This review establishes examples, not complete spell catalog verification. Preserve existing manual-roll, DM outcome, concentration and target rules; no forced Hit/Miss for spells without attack rolls.

### 13.3 Weapon requirements
- Inventory, sheet attacks, Battle options and attack drawer show weapon damage, ordinary properties, selected wielding mode and separate mastery effect/status. Name this Mastery, not mastery bonus. Show available/unavailable plus reason based on character feature and relevant selections, not ownership/proficiency alone.
- Offer One-handed / Two-handed only when the weapon/rules permit the choice. Two-Handed weapons have a fixed requirement, not a fictitious one-hand option. Two-handed use of a non-Versatile weapon does not invent an increased die. Validate known hand occupancy/shield conflicts before confirming mode changes or attack; preview any equipment change rather than silently removing equipment. Check detailed shield/equip timing and feature exceptions in the implementing content task.
- Longsword example: one-handed weapon die 1d8 Slashing; two-handed melee weapon die 1d10 Slashing. Keep the separate applicable ability/feature/item modifiers in final damage breakdown. Mastery Sap remains the same in either mode and applies only if unlocked and its trigger occurs.
- Display mastery trigger, outcome, duration, applicable limits and saves/DC where needed, derived from the individual mastery. Do not turn all masteries into hit-only triggers, numeric bonuses or generic expendable resources. Player records relevant DM outcomes; no enemy-state automation. Grip selection and mastery effects remain separate calculations with a common source used across screens.
