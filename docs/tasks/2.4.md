## Implementation and Developer handoff
Implemented design contract revision 2. Application `IDraftRecovery` holds raw name input and optional submitted character ID. Infrastructure `FileDraftRecovery` uses a version-1 bounded JSON journal beside the database, worker-thread IO, serialized access, flushed temporary writes and same-directory replacement. No database schema migration or dependency changes. Invalid input can be recovered but cannot create a character. Recovery input limit is 4096 UTF-16 code units; oversized input shows failure and remains editable. Original journal is retained on failed replacement; abandoned crash-time temporary files are ignored, not recovered.

Desktop maps recovery state to NewDraftPanel/RecoveryStatusText/RetryRecoveryCommand, with named polite live status. Creation persists its stable submitted identity before touching the library, checks for a prior matching result on retry, and clears recovery only after confirmed creation. A cleanup failure retains its submitted identity; retry reconciles instead of creating again. Name input is disabled for unresolved submitted creation. Closing drains pending creation/name writes; failed latest name persistence retains the open form for retry, while unreadable untouched recovery permits closing. Existing active-character selection does not redirect creation or recovery.

The journal is local recovery input, not a saved character, rules/catalog content, or backup archive. Normal close drains writes; abrupt termination can lose changes still visibly pending, while completed durable recovery is retained. Simultaneous app sessions sharing one journal are outside current verification; access is serialized within the recovery-store instance only. Adventure scoping and backup/restore integration remain future dependencies.
