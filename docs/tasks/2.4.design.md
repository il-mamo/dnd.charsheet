## Objective and boundaries
Recover the unfinished new-character name after interruption without implying that a character has been created. Preserve input and provide an explicit retry on failure. Creation retries must resolve the same submitted character, even after restart. Owner explicitly defers Adventure-scoped recovery to 2.6–2.7. No new recovery screen, modal, artwork, rules, or active-character changes. Existing character identity and library switching remain intact.

## Layout contract
Reuse the approved full-screen library at 1920x1080, 100% scaling. Preserve panel widths, shell, heading, name field, validation, library cards and creation-status location. Within NewDraftPanel reading order is heading, persistent name label, name input, name validation/help, recovery status, recovery Retry (only when relevant), Create draft / Retry create, then creation status. Status lines wrap to the panel width; no fixed-height clipping or horizontal scrolling. Use 12 DIP gaps and existing panel padding. Recovery retry is left aligned with the name input; its label is Retry, accessible name Retry draft recovery. Main creation button keeps PrimaryButton. Recovery Retry uses the existing secondary Button, minimum height 40, existing radius 4 and 1-DIP border. Status is Segoe UI 14 using Brush.TextSecondary; errors use Brush.Danger with explicit text. Existing focus/high-contrast resource styles apply. No new tokens. Keep creation and recovery status distinct: recovery status describes the name, creation status describes the saved character.

## State and validation matrix
| Trigger/state | Visible feedback | Enabled actions | Persistence / recovery |
|---|---|---|---|
| Loading recovery | Loading draft recovery… | Library actions remain available; name and creation disabled | Do not overwrite journal while unreadable |
| No unfinished name | Existing blank form; recovery line may be empty | Existing valid creation behavior | No invented recovered character |
| Name edited / recovery pending | Saving name… | Name remains editable; duplicate confirmation disabled during creation | Latest name wins; incomplete/invalid names remain recoverable input |
| Close requested with pending input | Saving name before closing… | Temporarily disable name/creation while draining; failure keeps window open with inline failure and Retry, then restores safe editing | Close only after latest pending input/creation is settled; untouched unreadable recovery permits close |
| Name durably retained | Name saved for recovery. | Normal form actions | This does not mean a character exists |
| Recovered unfinished name | Recovered your unfinished draft name. | Name editable; normal validation applies | Populate same existing input; no startup dialog or forced focus |
| Recovery save failed | Name could not be saved for recovery. + Retry | Preserve name and expose Retry; creation must first secure its durable intent | Never silently discard input or show saved |
| Recovery load failed | Draft recovery could not be opened. + Retry | Name/creation blocked; safe library actions available | Retry load; do not replace unreadable recovery |
| Creating draft | Existing saving feedback naming submitted target as appropriate | Name and creation disabled; selection cannot retarget write | Stable intent captured before create |
| Creation unresolved / restart with submitted intent | Draft creation could not be confirmed. Retry to check and finish. | Name frozen; Retry create enabled when idle | Reuse same submitted name/identity; no new duplicate |
| Confirmed created / cleanup retry required | Character saved. Finishing recovery… or Character saved. Retry to finish recovery. | No new creation until recovery bookkeeping resolved; retry remains available | Reconcile existing character; never create another |
| Creation fully finished | Existing success feedback; new-name field reset | Normal form | Clear recovery only after confirmed result; switching unchanged |
| Name invalid | Existing adjacent validation | Recovery may retain raw name; Create remains validation-gated | Restoring does not normalize or create invalid character |
| Character switched | Active identity updates normally | Safe library navigation | Name and pending creation remain separate from selected character |

No catalog-dependent state applies. No cancellation/destructive discard action is introduced. Do not silently clear recovery on Escape or application close.

## Keyboard and accessibility
Preserve current tab order, Enter-to-create validation and switch shortcut. Retry buttons use normal Tab/Space/Enter behavior, visible focus, and operation-specific accessible names. Enter in a frozen name input must not submit another intent; Retry create resolves the captured intent. Status changes must be exposed through polite live regions, without moving focus during background save. Errors carry textual meaning independent of color. Initial recovery restore must not steal focus from a user already interacting elsewhere. Existing system high-contrast styles and opaque reading surfaces apply. No new shortcuts or animation.

## Assets
None. Reuse existing shell, styles and portraits; no production artwork changes.

## Observable acceptance checks
- DES-2.4-01 (P01): Type an unfinished name, wait for successful recovery status, restart; same input is restored with recovery wording and no new character.
- DES-2.4-02 (P01): Force recovery write/load failures; show concise inline failure and keyboard-reachable Retry, preserve input, and never show false saved/empty success.
- DES-2.4-03 (P01/R01): Submit then simulate uncertain outcome; input freezes, Retry create resolves same identity once, including restart; active-character switching does not retarget it.
- DES-2.4-04 (P01): Creation success and cleanup failure distinguish saved character from unresolved cleanup; repeated retry never creates a duplicate.
- DES-2.4-05 (P06): At 1920x1080/100%, wrapped status and retry controls remain visible and keyboard operable; live error/save states and high-contrast focus are readable.
- DES-2.4-06 (R01): Recover a name while another character is active; header/library identity stays truthful, and no automatic activation occurs.
